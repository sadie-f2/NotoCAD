# UI enablement and dispatch — design

Phase 16. Nothing here is built. This is the shape to agree before code, because
menus and toolbars are the easiest thing in the project to accrete badly: they
duplicate the command registry, they grow a second dispatch path, and both
mistakes are expensive to undo once every entity has an icon.

Two audiences, deliberately not averaged together:

- **(a) Old hands.** Keyboard-first. Want file prompts that traverse
  directories without ceremony, and the R12/R2000 choice where the save is,
  not in a system variable they have to remember.
- **(b) Casual users.** Want to find LINE without knowing it is called LINE.
  Menus, a toolbar, and a file dialog.

The design goal is that (b) never costs (a) a keystroke, and that neither one
gets a code path the other does not use.

## 1. Enablement is system variables

No new mechanism. `OSMODE`, `PICKBOX`, `APERTURE`, `CURSORSIZE` and
`DXFVERSION` all arrived exactly this way: a row in `sysvar.cpp`, reachable
from AutoLISP through `getvar`/`setvar`, testable headless. UI switches are the
same kind of thing and should not invent a parallel preferences system.

Sadie's proposal was `icons(off, min, full)` and `menus(off, on)`. Mapped onto
names that already mean this in AutoCAD:

| Sysvar | Values | Meaning |
|---|---|---|
| `FILEDIA` | 0, 1 | 1 = file operations raise a dialog; 0 = they prompt on the command line |
| `MENUBAR` | 0, 1 | pull-down menus off / on |
| `TOOLBAR` | 0, 1, 2 | icons off / minimal / full |

`FILEDIA` and `MENUBAR` are real AutoCAD system variables with exactly these
meanings — worth taking rather than inventing, since anyone who has used AutoCAD
already knows them, and `FILEDIA 0` is the specific muscle memory of every old
hand who has ever scripted a save.

`TOOLBAR` as a 0/1/2 is the invention. R12 had no toolbar to name and modern
AutoCAD has no single three-state variable for one. It follows the `CURSORSIZE`
precedent — take AutoCAD's shape where R12 has no answer, and record that it is
a divergence — and it has the same 0/1/2 form as `UCSICON`, which already packs
off / on / at-origin into one integer.

**None of the three are saved in the drawing.** Same reasoning as `DXFVERSION`:
they describe how this session displays things, not anything about the
drawing's contents. Making them drawing variables would mean OPEN silently
resets the user's toolbar, which is the exact surprise `DXFVERSION`'s comment
already warns about.

That leaves persistence genuinely open — see §7.

## 2. Dispatch is a macro string, not a C++ call

**A menu item and a toolbar button carry the text a user would have typed, and
feed it to the same input pipeline.** R12 did this literally: a menu item was a
macro, `^C^CLINE`. Adopt it.

The alternative — a button calling `CommandEngine::begin(make_command("LINE"))`
directly — creates a second dispatch path, and second paths diverge. The first
time a menu item needs to answer a prompt as well as start a command, the direct
call has to grow its own sequencing logic and the two ways of running LINE stop
being the same thing.

What routing through the existing pipeline buys, at no cost:

- **Transparent commands work already.** The apostrophe convention lives in
  `PromptSession`; a `'ZOOM` menu item inherits it.
- **The command line echoes what the click did.** A casual user watching
  `LINE` appear when they press the line button is how they become an old hand.
  This is a real R12 virtue and it is free here.
- **It is testable headless.** A menu item is a string. A test can assert every
  macro in the table resolves to a registered command and parses, with no Qt
  and no display. A direct-call design can only be tested by building the GUI.

## 3. The UI is derived from the command registry

Today `command_names()` in `commands.cpp` is a flat `std::vector<std::string>`
of 58 entries and `command_aliases()` is the acad.pgp short forms. Neither
carries category or prominence.

**Enrich the registry rather than writing a menu table beside it.** Each command
gains a category (File, Draw, Modify, View, Format, Inquiry, Tools) and a tier
(`Hidden`, `Minimal`, `Full`).

- Menus are generated by grouping on category.
- `TOOLBAR 1` shows tier `Minimal`; `TOOLBAR 2` shows `Minimal` + `Full`. The
  min/full split is therefore *a property of each command*, not a second list
  that has to be kept in step with the first.
- A test asserts every registered command has a category and is reachable from
  exactly one menu, or is explicitly `Hidden`. This mirrors the existing
  discipline where `tests/test_registry.cpp` asserts the command count equals
  the version patch number: **adding a command cannot silently miss the UI**,
  because the suite fails until it is placed.

The metadata lives in core. `src/gui` reads it. No Qt type appears in the
registry, so the boundary in the build graph is unchanged — only artwork is
Qt-side.

## 4. File prompts: an advisory field, not a new PromptKind

`PromptKind` has seven values and none of them is FileName. The temptation is to
add one so the GUI knows to raise a dialog. **That would be wrong, by the
reasoning already recorded at `command.hpp:58-62`**: `RubberBand` was
deliberately kept *out* of `PromptKind` because the distinction was "purely
about display", and `prompt_takes_point()` and the input parser both switch on
the kind and should not be dragged into display questions.

A filename is a `String` answer. Whether it arrives by dialog or by typing is
display. So it takes the same shape as `rubber_band`: an advisory field on
`Prompt` that the engine never reads.

```
enum class FileHint : std::uint8_t { None, Open, Save };
FileHint file_hint{FileHint::None};
std::string file_pattern;   // "*.dxf", "*.lsp"
```

The terminal ignores it entirely and reads a string, exactly as now. The Qt
command line sees it and, **if `FILEDIA` is 1**, raises a `QFileDialog` whose
answer is supplied to `CommandEngine::supply()` as an ordinary string. With
`FILEDIA 0` the GUI behaves like the terminal. One command implementation, three
front ends, no branch inside the command.

## 5. Completion and traversal — and a conflict to settle first

**This is the one request that touches a settled decision.** CLAUDE.md says, in
terms: *"No terminal UI work. The GUI is not driven from a terminal, so raw
mode, termios and libedit are all off the table... live completion is a Qt
widget concern where it is free."* Tab completion in `ncad` needs raw mode to
intercept Tab at all. Taken literally, the request and the rule collide.

They do not have to. R12's own idiom for "show me what is available" is **`?`**,
not Tab — `LAYER ?` lists layers — and this project already owns a wildcard
matcher, used by `ssget` filters and by LAYER, with a suite in
`test_wildcard.cpp`.

So:

- **Core** gains one service: `list_matching_paths(pattern)`. No Qt, no termios,
  testable headless.
- **Terminal.** At a file prompt, `?` lists the directory and a wildcard
  (`src/*.dxf`) lists matches, then re-asks. Directory traversal is just typing
  a path with a trailing separator and `?`. Costs no raw mode and is more R12
  than Tab would have been.
- **Qt.** Tab completion in the command line widget, against the same service.
  Free there, exactly as CLAUDE.md predicted.

One service, two presentations, and the settled decision stands unamended. If
Sadie wants literal Tab in the terminal anyway, that is a deliberate reversal of
a recorded decision and should be taken as one — not smuggled in as a file-ops
convenience.

## 6. R12 / R2000 at the point of saving

Sadie's framing: R12 is the lingua franca for parts libraries, so `DXFVERSION`
does not hurt in the short term. Agreed — which means this should be additive
and must not disturb what works.

**Do not add a mandatory prompt step to DXFOUT.** Every existing
`(command "DXFOUT" "f.dxf")` in LISP supplies exactly one answer; an extra
question the engine asks is an extra answer scripts do not provide, and they
would hang or fail. That is a real compatibility break for the exact automation
path this project exists to serve.

Three surfaces, one concept, none of them mandatory:

1. **Sysvar** — `DXFVERSION`, unchanged. Scripts keep working untouched. It
   already survives OPEN by design (verified 2026-08-01).
2. **Keyword option** — the existing filename prompt gains a keyword:
   `File name or [Version] <drawing.dxf>:`. Typing `V` toggles R12/R2000 inline.
   Costs a script nothing, because a keyword is only consumed if offered.
   This is the old-hand answer.
3. **Dialog filter** — the `QFileDialog` from §4 carries two name filters,
   "AutoCAD R12 DXF (*.dxf)" and "AutoCAD 2000 DXF (*.dxf)", and the chosen
   filter sets the version for that write. This is where a casual user meets the
   choice without having to know it exists.

All three resolve to the same `DXFVERSION` value, so there is one answer to
"what will this write?" and `SETVAR` still reports it.

## 7. Open — needs Sadie, not code

- **Where do UI preferences persist?** The three sysvars are session-scoped by
  §1, and the project has no settings file. R12's answer was `acad.lsp` — a
  startup script that runs `setvar` calls. That needs no new mechanism (`ncad`
  already takes a positional LISP file) and is idiomatic. The alternative is
  `QSettings`, which is Qt-side only and would mean the terminal and the GUI
  remember different things. Leaning strongly toward the startup LISP.
- **What is in `Minimal`?** Proposed first cut, roughly R12's default screen
  menu: LINE, CIRCLE, ARC, PLINE, TEXT / ERASE, MOVE, COPY, TRIM, EXTEND /
  OPEN, SAVE, ZOOM, PAN. Everything else `Full`. This is a taste call.
- **Where does icon artwork come from?** Three options: stroke paths drawn with
  the existing renderer (no new dependency, no third-party licence, consistent
  with the Hershey decision and keeps `ABOUT`'s licence roster honest); SVG
  (adds QtSvg); PNG resources (adds an asset pipeline and a licence to track).
  Leaning to stroke paths — the machinery to draw them already exists.
- **Screen menu?** R12's side menu is a distinct thing from pull-downs. Is it
  wanted, or are pull-downs plus a toolbar the whole of it?
- **Defaults.** Suggest `FILEDIA 1`, `MENUBAR 1`, `TOOLBAR 1` in the GUI, and
  all three inert in the terminal — `ncad` should look exactly as it does today.
